# News AI Agent — Project Context

Dutch-language social media automation: scrapes NOS/RTL news + 8 NL event sources, generates AI content with Claude, publishes photo posts and Reels to **Instagram** and the same Reels as **YouTube Shorts** — 2× daily for news, weekly for events on Thursday (events go to Instagram + Facebook, but not YouTube). **The weekly events post is currently disabled** (feature flag `ENABLE_EVENT_POSTS`, default off — deprecated for low engagement); see the flag note below.

---

## Lambda Functions & Handlers

| Handler | File | Schedule | Purpose |
|---|---|---|---|
| `lambda_handler` | `lambda_handler.py` | EventBridge 2×/day + events | Main pipeline: scrape → AI → publish photo or Reels |
| `reels_worker` | `src/reels_worker.py` | Invoked async by main handler | Publishes Reels to Instagram (polls container status) |
| `youtube_worker` | `src/youtube_worker.py` | Invoked async by main handler | Uploads same Reels video as YouTube Short |
| `token_refresher` | `token_refresher.py` | EventBridge every 30 days | Refreshes Instagram 60-day token before expiry |
| `handler_metrics_collector` | `lambda_handler.py` | EventBridge daily 02:00 AMS | Fetches Instagram Insights, writes to DynamoDB |
| `handler_analytics_engine` | `lambda_handler.py` | EventBridge Sunday 22:00 AMS | Claude analytics + prompt auto-update + SNS email |
| `handler_selection_review` | `lambda_handler.py` | EventBridge Sunday 19:00 AMS | Weekly editorial review: digests the week's article picks + top-7 runner-ups + engagement, emails an Opus growth/commercial review |

**Run mode detection** in `lambda_handler`: `event.get('format') == 'event_post'` → events pipeline (**gated by `ENABLE_EVENT_POSTS`, default off** — returns `skipped` without building the AI agent or scraping when disabled); `event.get('format') == 'daily_fact'` → daily Dutch-fact Story pipeline; `event.get('format') == 'fact_carousel'` → weekly Dutch-fact carousel feed post (gated by `ENABLE_FACT_CAROUSEL`); `event.get('format') == 'reels'` → Reels mode; otherwise → photo post.

## Deployment (CI/CD)

**Every push to `main` auto-deploys to AWS.** `.github/workflows/deploy.yml` runs on push: it first runs the test job (`pytest tests/`), then — only on push to `main` — builds the ZIP (`scripts/build_lambda.sh`) and runs `terraform apply -auto-approve` (AWS auth via OIDC). There is no separate manual deploy step; merging/pushing **is** the deploy. A deploy typically lands a few minutes after push — confirm via the function's `LastModified` (`aws lambda get-function-configuration --function-name news-ai-agent --query LastModified`). Pull requests run the tests only (no deploy). So: never push to `main` expecting code not to ship, and if a change breaks a scheduled run, the fix must be pushed (and the deploy confirmed) before re-triggering the Lambda.

**Four jobs: `test`, `lint`, `code-quality`, `deploy` — and `deploy` needs only `test` + `lint`.**
The split is deliberate: **block on facts, mail on judgements.**
- **`lint` BLOCKS** — `ruff check` (rule set `E4,E7,E9,F,B`, deliberately narrow so it can hold at zero), `bandit -lll` (HIGH severity only; there are 22 MEDIUM, 19 of them `requests` calls with no timeout), `pip-audit` (`continue-on-error` — a CVE in a transitive dep is not a reason to block an unrelated fix). Blocking a deploy is safe here: no deploy just means the previous working version keeps running on its cron.
- **`code-quality` NEVER blocks** and `deploy` does not depend on it. It scores 7 metrics + coverage, appends to `code_quality/history.json` in S3, and emails on regression. Gating a no-rollback auto-deploy on a *ratchet* metric would let one legitimate refactor block a production hotfix.
- Widening the ruff rule set means one cleanup commit per family — `E501`/`UP`/`I`/`SIM` currently report ~700 findings between them, so enabling one without the cleanup turns the blocking gate permanently red, which is how gates get switched off.

**The GitHub OIDC deploy role is NOT in Terraform.** `grep -rn 'aws_iam_role"' infrastructure/terraform/` returns only `lambda_role` and `glue_role`. The role that runs `terraform apply` exists solely as `secrets.AWS_ROLE_ARN` — it is the most privileged credential in the system and the one thing not auditable from the repo. `gate.py` therefore fails **soft** on S3 write errors (warns, exits 0) rather than assuming permissions; see `local_only/ci_role_policy.md`.

## Key Architectural Decisions

**Reels publishes via separate Lambda (`reels_worker`)**
Meta's video processing takes up to 10 minutes. Main Lambda has 15-min hard limit. To avoid timeout, main handler generates video, uploads to S3, then invokes `reels_worker` asynchronously (fire-and-forget). `reels_worker` polls the Instagram container status up to 80×8 seconds.

**YouTube Shorts via separate Lambda (`youtube_worker`)**
The same MP4 already in S3 is also published to YouTube Shorts. Main handler invokes `youtube_worker` asynchronously immediately after invoking `reels_worker` — both are fire-and-forget. YouTube failure never blocks Instagram: the invoke is wrapped in its own try/except. Events content is intentionally excluded (static slideshow format performs poorly on YouTube Shorts; misaligns with the news-channel identity needed for monetization).

**News Reel render — single ffmpeg pass, not moviepy (`src/video/ffcompose.py`)**
The final video assembly for news Reels is done in **one ffmpeg `filter_complex` pass**, not moviepy's `write_videofile`. moviepy composited every frame in pure Python (single-thread) and took ~9 min for a ~35 s clip — ~85% of pipeline time and the main cause of 15-min Lambda timeouts. Key insight: every visual layer is a **static image over a time window** (gradient is time-invariant; each subtitle chunk and the hook are fixed PIL PNGs; all full-width, x=0). So `_build_background` (`creator.py`) returns a background **mp4 path** (stock → `_stitch_clips_to_file`; photo/Ken Burns → `render_ken_burns_mp4`; fallback → `render_fallback_bg_mp4` — all ffmpeg), `effects.build_subtitle_overlays`/`build_hook_overlays`/`render_gradient_png` emit RGBA PNGs as `OverlaySpec(png_path, y, start, end)`, `mix_audio` is written to a file, and `ffcompose.assemble_reel` burns them with `overlay=0:y:enable='between(t,s,e)'` + one x264 encode (same settings as before → pixel-equivalent, no quality loss). Render drops to ~1-2 min. **Only the news Reel path uses this**; `create_fact_video` (daily Story) still uses moviepy (`compose_stock_scenes`/`make_ken_burns_clip`/`make_fact_overlay` are kept for it) — shorter clips, lower risk; can migrate later (helpers are reusable).

**Multi-channel publishing — Publisher adapter + CrossPoster (`src/publishing.py`)**
Whatever is published to Instagram is mirrored to every other configured channel via a single dispatcher. `ChannelPublisher` is the common interface (`name`, `supports(kind)`, `publish(kind, media_url, caption, dry_run)`); `kind ∈ {REEL, PHOTO, STORY}`. Concrete adapters live in `src/social_publisher.py`: `InstagramPublisher` (primary), `FacebookPublisher` (secondary), and `LinkedInPublisher` (secondary, REEL only). `CrossPoster.publish(kind, …)` fans out to the primary (failure surfaced via `primary_error`) + every secondary that `supports(kind)` **best-effort** (logged + alerted, never blocks); it returns `{"results": {channel: result}, "primary_error": Exception|None}`. `build_crossposter(content_source="news")` registers the primary plus any secondary whose creds are present (`FACEBOOK_PAGE_ID` → Facebook; `ENABLE_LINKEDIN=true` **and** `LINKEDIN_ACCESS_TOKEN` + `LINKEDIN_ORG_ID` → LinkedIn — the flag lets the code ship dark, default off). **Adding a channel = write one `ChannelPublisher` adapter + one line in `build_crossposter()`; call sites never change.** Call sites: `reels_worker` (Reel + Story), `_run_event_pipeline` (event Reel — passes `content_source="event"`), photo branch in `lambda_handler`. Facebook: news/event Reels → **FB Reel** (`video_reels`), photos → **FB photo** (`/photos`), daily Story → **FB Story** (`video_stories`); Page token derived at runtime from the user token (`pages_manage_posts` scope). Meta video flows follow Meta's two-phase upload: `start` → hosted `file_url` upload → poll status → `finish`. **LinkedIn: news Reels only** (event slideshows excluded, same rationale as the YouTube exclusion — the event pipeline opts out via `content_source="event"`); posts to a Company Page (`urn:li:organization:<id>`, `w_organization_social` scope). Unlike Meta, LinkedIn's Videos API needs the raw **bytes**, so the adapter downloads the presigned S3 URL into memory then does `initializeUpload` → PUT byte ranges (collect ETags) → `finalizeUpload` → poll until `AVAILABLE` → create `/posts`. **When new channel SDKs push the Lambda ZIP past 250 MB, migrate to a Lambda Container Image (ECR) — not microservices.**

**Daily Dutch-fact Story (story-only, feature-flagged)**
Every day at 07:00 Amsterdam (EventBridge `{"format":"daily_fact"}` → `_run_daily_fact_pipeline`), a curated "Did you know?" Dutch fact is rendered as a short vertical video (Pexels Dutch B-roll + on-screen text + `FACT_STORY_MUSIC`, **no TTS**, no baked-in branding since IG shows the account in the Story's top-left) and published as an **Instagram Story only** — no Reel, no YouTube. Duration = reading time of the text (`reading_seconds()` in `video/config.py`) so it's short enough to watch to completion. Deliberately not a Reel: news already posts 2 Reels/day and a 3rd would cannibalize reach; Stories are a separate surface. Story video is published via `reels_worker` (async, `publish_story=True, publish_reel=False`) so Meta's video processing happens off the main Lambda's clock. When `FACEBOOK_PAGE_ID` is set, the same video is also cross-posted as a **Facebook Page Story** (`FacebookPublisher.publish_story` → Graph API `video_stories` start→file_url upload→finish; Page token derived at runtime from the user token, requires `pages_manage_posts`). The Facebook leg is best-effort — a Facebook failure never blocks the Instagram Story. Gated by `ENABLE_INSTAGRAM_STORIES` (Secrets Manager) — when off, the pipeline returns immediately and generates **nothing** (no fact pick, no Pexels, no render). Fact pool lives in S3 `facts/pool.json` (hot-editable, seeded from `DEFAULT_FACTS` in `src/dutch_facts.py`); least-recently-used rotation in `facts/_rotation.json` means a fact repeats only after ~the whole pool cycles (~90 days). When the pool nearly cycles, a one-time SNS refill email is sent to `ALERT_EMAIL`; if ignored, facts simply repeat (system never stops, AI never auto-generates facts).

**Weekly Dutch-fact carousel (feed post, feature-flagged)**
Every Sunday 12:00 Amsterdam (EventBridge `{"format":"fact_carousel"}` → `_run_fact_carousel_pipeline`), the facts shown in Stories over the last 7 days are collected (`dutch_facts.get_weekly_facts` reads the same `facts/_rotation.json` the Story pipeline writes) and published as **one Instagram carousel (album) feed post**. Rationale: the daily fact **Story reaches only existing followers** (Stories are never served to non-followers, and the API can't add poll/link/hashtag stickers), so its evergreen, saveable content is wasted as a growth lever. A **carousel is a discovery + save surface** (feed/Explore reach non-followers; educational "collections" get saved), builds the grid (profile→follow conversion), and — unlike Stories — is **auto-tracked by `metrics_collector`** (it appears in the media edge). Repeating facts followers already saw in Stories is intentional: the feed/Explore audience is different and a week-recap is inherently saveable. Cards are static **1080×1350 (4:5)** PIL images (`video/fact_card.py`, `render_fact_carousel`) matching the Story palette. Each fact card sits on a **relevant Pexels photo background** fetched from that fact's `footage_queries` (`footage.fetch_pexels_photo` — the same visual source the Story video uses), darkened with a scrim + text shadow for legibility; a missing photo falls back to a solid brand card. **Slide 1 carries the brand heading above the first fact** (not a title-only cover); the final slide is a follow CTA with its own special Pexels image + the **brand logo** — a round-cornered squircle badge resolved by `config.brand_logo_path()` (prefers a `squircle`/`round` PNG in `src/logo/`, else the raw source, else a "DUTCH DAILY" wordmark); overridable via `BRAND_LOGO_PATH`. **No @handle** is drawn on any card — Instagram shows the account at the top of the post already. **No music** — IG's publishing API can't add audio to a static-image carousel (would require video slides); for read/save content it's cosmetic. Published **Instagram-only** via `InstagramPublisher.publish_carousel` (Graph API 3-step: per-image `is_carousel_item` child containers → `CAROUSEL` parent → publish) — carousels don't fit the single-`media_url` CrossPoster fan-out, so no cross-post/YouTube. Caption via `NewsAIAgent.generate_carousel_caption` (prompt `carousel_caption.txt` / `AI_PROMPT_CAROUSEL_CAPTION`, template fallback). **Enabled by default** (`ENABLE_FACT_CAROUSEL`, default `true` in code — set `ENABLE_FACT_CAROUSEL=false` in Secrets Manager to disable); needs ≥3 facts in the window or it skips (`MIN_CAROUSEL_FACTS`). Depends on the Story pipeline to populate rotation. Source card images upload to `facts/carousel/` in S3 and are archived to Glacier after 90 days (Terraform lifecycle) since Instagram hosts its own copy after publish.

**Failure visibility — alert on the symptom, not just the causes**
Every push to `main` auto-deploys with no approval, no rollback and (until now) no post-deploy check, so a bad commit reaches production unattended. The alerting was entirely **cause-based** — each known failure mode had a `try/except` that emailed — which by definition cannot cover an unforeseen regression. Four layers now close that:
1. **Drought watchdog (the catch-all)** — `MetricsCollector.check_publish_drought()` runs inside the daily 00:00 UTC collector on the media list `collect()` already fetched (no new schedule, no extra API call) and emails when Instagram's newest post is older than `PUBLISH_DROUGHT_HOURS` (**30**, read at call time), or when the account has no post at all in 30 days. It verifies **at the destination**, so it catches every failure class without asking why — including ones not yet imagined. Do **not** point this at `posts_*.json`: that file is written even when publishing later fails, so S3 cannot answer "did we publish".
2. **Every "published nothing" exit alerts** — `all_duplicates`, `no_posts` and `quality_gate_rejected` in `lambda_handler` used to return HTTP 200 in silence; they are the most likely outcomes of a regression in the scraper, the AI agent or the quality gate. Each now sends one email naming the stage. This is the *fast, specific* layer; the watchdog is the slow, total one.
3. **CI smoke test** — `{"health_check": true}` returns `{'status':'healthy'}` right after `get_secrets()` and before any work; `deploy.yml` invokes it after `terraform apply` and fails the build on `FunctionError` or an unexpected body. Catches broken imports/handlers in under a minute instead of at the next cron (up to 13 h later). Use the dedicated payload — reusing a flag-disabled pipeline would turn the smoke test into a real publish the day the flag flips.
4. **The main handler re-raises after alerting** — returning a 500 dict looked like a *success* to Lambda, which zeroed the `Errors` metric, disarmed `news-ai-agent-lambda-errors` and stopped the on-failure destination from firing, leaving in-code SNS as the single notification path. Raising restores those three AWS-side signals as an independent channel. **Safe only because main runs with `maximum_retry_attempts = 0`.**

**The async workers must NOT re-raise** (`reels_worker`, `youtube_worker`): they run with `retries = 2`, and a failure *after* Instagram accepted the container would republish. Their alert-and-return-500 shape is deliberate. This asymmetry is the easiest thing to "fix" wrongly.

**Viral-skip guard — give a viral post the next slot (`src/viral_guard.py`)**
News posts 2×/day. When a post goes viral, publishing the next one splits the follower engagement that fuels the algorithm's distribution ramp and buries the viral post on the profile grid exactly when profile-visit→follow conversion peaks. `should_skip_next_post(bucket)` runs **inline at the top of the news pipeline** (`lambda_handler`, right after the format dispatch, before STAGE 1) — deliberately **not** a separate scheduled job: it only costs 2 Graph API calls on runs that would post anyway, and a skip costs nothing (no scrape, no Claude, no render). It skips the run iff the latest post is **< `VIRAL_WINDOW_HOURS` (24 h)** old **and** its live engagement (likes+comments+shares+saves) is **≥ `VIRAL_SKIP_MULTIPLIER` (5×) the median** of the last 30 days **and** **≥ `VIRAL_MIN_ENGAGEMENT` (1000)** absolute. Both conditions are required: the multiplier alone misfires on a small sample, the absolute floor alone stops working as the account grows. Guardrails: **exactly one slot is skipped per viral post** (the media id is recorded in S3 `viral/_skip_state.json` — the same id never triggers twice, so cadence can never collapse); a **≥10-post baseline** is required; and every failure path is **fail-open** (a Graph/DynamoDB/S3 error logs a warning and posts normally). A skip emits a structured `viral_skip` log plus an informational SNS email. Applies to the **news pipeline only** — the daily fact Story and weekly carousel are separate surfaces that don't compete. Flag `ENABLE_VIRAL_SKIP`, **default on**.

**Model per role, and `VISION_MODEL` is split out on purpose** (retuned 2026-08)
Everything ran on `claude-opus-5` from the Opus 5 migration until this retune. Retuned again on 2026-08-23 for cost (see below). Now: **Opus 5** for `CONTENT_MODEL` (batch selection — the editorial brain; its model *is* the product), `ANALYTICS_MODEL` (it auto-edits production prompts) and `SELECTION_REVIEW_MODEL` (weekly, negligible cost). **Sonnet 5** for `VISION_MODEL` (the footage gate — see the cost note below), `REVIEW_MODEL` (quality_check rewrites one short post) and `FOOTAGE_QUERY_MODEL` (structured extraction — the safety *decision* is made in code by `footage_geo.derive_place_mode`, not by the model).

**`VISION_MODEL` is a NEW knob split out of `REVIEW_MODEL`, and the split is the whole reason the retune is safe.** Those three roles shared one variable, so lowering `REVIEW_MODEL` to save money on `quality_check` would silently have downgraded the vision gate too — a change that looks like a cost tweak and lands as a correctness regression, surfacing weeks later in the comments. `tests/test_model_migration.py` pins both halves.

**All model knobs are copied by `get_secrets()`**, so a model swap is a Secrets Manager edit with no deploy. They were *not* before this change: the defaults in `ai_agent.py` were the only way to set them, i.e. deploy-only despite being documented as hot-tunable — the same trap CLAUDE.md already records for the viral and content-mix thresholds.

**Every call goes through `NewsAIAgent._create(role=, model=, max_tokens=, effort=)`.** It sets `output_config.effort` (no call site set it before, so all nine ran at the API default `high` with adaptive thinking billed into `max_tokens`) and emits a structured `claude_usage` log line with tokens and an estimated cost per role. Effort degrades **once, process-wide**, if the SDK or a model override rejects `output_config` — a systematic 400 would otherwise push every call site into its own fallback and quietly disable the agent. `requirements/*.txt` pin `anthropic>=0.79.0` for that reason.

**The real cost driver is the vision payload, not the model.** `VALIDATION_BATCH = 15` full-size Pexels preview JPEGs, 0–2 calls/run, 2 runs/day = up to 60 images/day at up to ~4,784 tokens each. `footage.thumbnail_for_vision()` rewrites Pexels URLs to `w=640` before sending — quality-neutral for a PASS/FAIL judgement, and a bigger saving than any model swap. `VALIDATION_BATCH` is deliberately **not** lowered: a thinner batch pushes the search into the escalation ladder more often, which costs an extra vision call.

**Opus 5 API rules baked into the code — keep them when adding calls:** (1) `temperature`/`top_p`/`top_k` return 400 — never pass them; (2) thinking is ON by default and thinking blocks precede text in `response.content` — always extract text via `NewsAIAgent._response_text()` (or an equivalent type-filtered scan), never `content[0]`; (3) `max_tokens` caps thinking + response together — budgets are sized with headroom (2000-8000), don't shrink them back; (4) safety classifiers can return HTTP 200 with `stop_reason == "refusal"` — `_response_text` logs it and returns `""`, letting each call site's existing fallback handle it.

**Prompts stored in Secrets Manager**
All prompts (`AI_PROMPT_BATCH_SELECTION`, `AI_PROMPT_SINGLE_ARTICLE`, `AI_PROMPT_QUALITY_CHECK`, `AI_PROMPT_EVENT_SELECTION`, `AI_PROMPT_CAROUSEL_CAPTION`, `AI_PROMPT_FOOTAGE_QUERIES`) are stored in Secrets Manager alongside API keys. `get_secrets()` in `lambda_handler.py` loads them as env vars at startup. `ai_agent.py` reads from env, falls back to `prompts/` directory files (`prompts/*.txt` are gitignored; only `*.txt.example` are tracked, so production reads the Secrets Manager value). This allows hot-updating prompts without redeploying Lambda. **`AI_PROMPT_FOOTAGE_QUERIES` is the one exception to "env or file or bust"**: it loads via `_load_prompt_or()`, which falls back to the `_FOOTAGE_QUERIES_PROMPT` constant in `ai_agent.py` instead of raising. If it raised, a deploy landing before the secret was written would drop the pipeline back to Dutch-headline keyword extraction — the exact wrong-city bug the prompt exists to prevent.

**Token refresh is a separate Lambda**
Instagram access tokens have a 60-day TTL. A dedicated Lambda runs every 30 days to exchange the token via Meta Graph API and write the new token back to Secrets Manager.

**Duplicate detection**
On every run, main handler reads all `posts_*.json` files from S3 to build a set of published URLs and filters them out before AI processing. No database needed — S3 scan is acceptable at this volume. Additionally, `original_title` values from posts published in the last 3 days are passed to `batch_selection` as context so the AI skips articles covering already-published topics even when they come from different sources (cross-source semantic dedup). This is a **soft prompt instruction**, not a hard filter, and it is **topic-arc shaped, not title-shaped**: it blocks only the **same event told from the same angle** within 72 h (the same match result/accident/announcement re-reported), and explicitly **permits a continuation when there is a new hard number or escalation** — a new record, a next stage, a new consequence, new damage, casualties. A covered heatwave does not suppress the storms that end it. When a continuation is chosen, the prompt requires the `hook` to open with the **escalation frame** ("Last week X — today Y"), because a follow-up that doesn't name the previous stage reads as a repeat. Refined after a storm/windmill story was wrongly skipped as "same as" a prior heat story.

**Editorial pool filters — enforced in code, not the prompt (`src/news_scraper.py`)**
Rules an LLM can quietly drop belong in Python; only judgement belongs in the prompt. Two hard filters run in `lambda_handler` next to the URL dedup:
1. **`is_non_story_title()`** drops recurring NOS/RTL *formats* that read like news but make terrible standalone posts — `Wekdienst`/`Weekdienst`, `In beeld |`, `Live |`/`Liveblog`, `Podcast`, `Explainer |`, `in Nieuwsuur`. Three of one review week's engagement-floor posts were exactly these. Note this drops liveblogs of genuine breaking stories too — an accepted trade, since a rolling liveblog page makes a poor 35-second Reel.
2. **`collapse_near_duplicates()`** clusters headlines covering one event so the AI sees real pool depth (27 scraped → ~21 options on a live pool; three AZ/PSV match reports become one). Similarity is the **overlap coefficient** `|A∩B| / min(|A|,|B|)`, **not Jaccard**: outlets write the same story at very different headline lengths, and Jaccard's union term punished exactly that — a measured same-event pair scores 0.29 by Jaccard but 0.44 by overlap, while the closest genuinely-different pair sits at 0.29. Threshold **0.40** sits in that gap, plus a ≥2-shared-token floor so one word can't score 1.0 on a short headline. **Calibrate any change against a live pool** — the first 0.6-Jaccard version was a silent no-op.

Both filters **fail open**: if a filter would empty the pool, everything is kept and a warning is logged. `all_duplicates`/`no_posts` alert and re-raise, so an over-eager filter would otherwise cost a missed slot plus a false alarm. Excluded articles are **tagged with `excluded_reason` and still written into `articles_*.json`** (and surfaced to the weekly review as `excluded_from_pool`) — without that the review cannot tell whether a filter over-fired.

**Slot briefs + rolling content mix — computed facts, injected as prompt text**
The EventBridge payload's `schedule` (`morning`/`evening`) selects an editorial brief: 09:00 AMS = "what changes for you today" (prices, strikes, warnings, travel, rules taking effect), optimised for **saves**; 19:00 AMS = the biggest national story, optimised for **shares/comments**. Manual invokes default to evening. Separately, `build_content_mix_brief()` turns the rolling 7-day topic history into a constraint: the actual distribution, a **≥40% crime cap** ("do not select another crime story unless national in scale"), a "no second violence post today" line, and the target mix (~40% impact-on-you / 30% security-crime / 20% NL identity / 10% money-business). The cap is **stated, not hard-filtered** — dropping crime articles from the pool would suppress a genuine national emergency, so the code owns the arithmetic and the model owns the exception. Topics come from the shared `metrics_collector.classify_topic()` (same keyword map as analytics), are persisted as `topic` on each post at publish time, and are collected by the **same single S3 scan** `get_published_urls()` already does — it now returns a 4th element `recent_topics` rather than adding a second listing.

Two more caps were added after a measured regression: a **`TOPIC_SHARE_CAP` (30%) on *any* topic** and a **`SERIES_MAX_DAYS` (4) run limit per named series**. The crime cap was the only cap that existed, so the brake sat on the one high-variance category while everything else ran free: Weather went from 10% to 30% of output, the `Nederland Droogt Uit` serial ran 13 posts over 14 days, and median reach halved. Topic saturation also needs an absolute floor (`_MIN_SATURATION_POSTS = 3`) — in a thin window one post is 33%, and one post is not a story arc. The series run is counted in **days, not posts**: the account publishes twice daily, so "13 posts" and "13 days" are very different fatigue signals and the one the viewer feels is days. `recent_topics` entries became `(topic, datetime, series)` triples (2-tuples still accepted) so the series run needs no second S3 listing. Replayed against the real July–August history the new caps fire on 11 of 38 days — none of them before 08-04, i.e. none during the healthy high-reach period.

**Engagement CTA + named series — separate fields, never inside `content`**
Every post carries a `cta_question` (one short question answerable from the viewer's own life) and a `save_prompt`, plus an optional `series` from a **fixed two-name list** (`"Wat Verandert Er Vandaag"`, `"Nederland Droogt Uit"` — an invented name is dropped at parse time, since a one-off series is worse than none). They are deliberately **not** part of `content`: the quality gate only ever sees `post.content`, so keeping the CTA out of it means the "no calls to action" neutrality rule needs no carve-out and the news body keeps its BBC/Reuters register. `format_post()` appends them to the caption (series leads, its hashtag is added); `creator.create_news_video` speaks the `cta_question` as the closing line — appended **after** `cap_narration()`, because that function drops trailing sentences and a pre-cap CTA would be the first casualty. CTAs are written in English to match the rest of the content, not Dutch.

**Editorial selection transparency + weekly review**
`batch_selection` returns, alongside the chosen article, a `selection_reason`, a `personal_stake` score, a `share_potential` score and a `runner_ups` array — together the **top-7** pool candidates with their Tier, both scores and why-not — persisted into `posts_*.json` and emitted as a structured `selection_decision` CloudWatch log (survives S3 pruning; back-compat: absent on pre-update runs). The review also receives `slot`, `topic`, `series` and `excluded_from_pool`.

**The ranking has TWO axes of equal weight, and the second one exists because the first one alone was measured to be harmful.** `personal_stake` is the **SAVE** score (0–3: costs money / changes commute / threatens your street / sets a date to remember). `share_potential` is the **SHARE** score (0–3: anomaly or record / a nationally recognised name or moment / a reaction someone wants to voice / a "look at this" frame). Stories rank on the **sum**, and a story scoring 0 on **both** is never selected even if it is the only Tier 1 left. The tiebreaker is **slot-dependent**: morning (09:00, save-optimised) still favours "has a date the viewer can act on"; evening (19:00, share-optimised) favours the higher share score. Tier 1d cost-of-living still ranks above Tier 2e security, but the **Tier 2e locality floor now yields to a share score of 2+** — a local incident people talk about travels regardless of how many postcodes it touches.

Why: a save-only ranking shipped for three weeks and the account's median **shares per 1 000 reach halved (9.8 → 5.2)** while saves per 1 000 stayed flat (2.0 → 2.1) and average watch time did not move (13 357 → 13 506 ms). Posts above 8 000 reach went from **8-in-41 to 0-in-37**, and weekly follower growth fell +266 → +107. On this account reach tracks **shares** (Spearman 0.86 across 123 Reels) and every breakout broke out on shares — so optimising saves optimised the one signal that could not warn anyone it was going wrong. Crime/Security dropped 34% → 16% of output under the locality floor and the median reach of the crime stories still chosen fell 2 988 → 945. A separate weekly Lambda (`handler_selection_review` → `src/selection_reviewer.py`, Sunday 19:00 AMS) pairs each week's pool (`articles_*.json`) with its pick, joins Instagram engagement (DynamoDB `post-metrics`, best-effort caption/time match), and emails the most advanced Claude (`SELECTION_REVIEW_MODEL`, default `claude-opus-5`) acting as a growth/content/platform/commercial panel — surfacing weak picks, missed high-engagement candidates, and concrete prompt/dedup/schedule revisions to drive follower growth toward monetization. Reports only; never mutates prompts.

**The reviewer's engagement payload is load-bearing.** It originally carried `reach`, `saves`, `comments` and `normalized_engagement_rate` — but **not `shares`**, the metric that actually predicts reach here. A panel that cannot see shares recommends save-optimisation by default, and that is precisely how the regression above was authored: the review proposed it, the prompt adopted it, and no metric in the review's own field of view moved. `_attach_engagement` now also passes `shares`, a derived `shares_per_1k_reach`, `likes`, `video_views` and `reach_amplification`, and the prompt states the measured correlation and instructs the panel to judge every recommendation against shares-per-1k **first**. **Before adding a rule to the selection prompt, check that the metric it optimises is one the reviewer can see** — otherwise the loop has no way to notice it is wrong.

**Cover de-duplication (Reels)**
Same problem, visual layer: similar news (heatwaves, weather) used to reuse the identical Pexels cover clip. Two defenses, both fed by the same `get_published_urls()` S3 scan (now also returns footage fingerprints from posts in the last `FOOTAGE_REUSE_WINDOW_DAYS`, default 30):
1. **Real photo preferred as cover.** When the article's own image is *fresh* it becomes the cover (Ken Burns) with Pexels stock filling the body — `creator._build_background` hybrid. Freshness = its URL wasn't used recently **and** it isn't a perceptual near-duplicate of a recent cover (`effects.compute_dhash`/`hamming`, threshold ~10) — this catches NOS's recurring "weekdienst" template card even at a different URL.
2. **Pexels id fresh-first.** When stock clips are used, ids from the reuse window are moved to the back of the candidate list (not hard-filtered) so the cover is fresh but the body never degrades to a gradient when the pool is small. `footage.fetch_stock_clips` records the ids actually used.
Each Reel post persists `pexels_media_ids`, `cover_image_url`, `cover_image_hash` into `posts_*.json` for the next run's scan. News Reels only (events/daily-fact opt out).

**Geographic footage safety — never claim the wrong place (`src/footage_geo.py`)**
Viewers were commenting that a story about a specific city/region/port showed footage of a *different* one, and reading it as "the AI generates fake images". An audit of 50 posts found 70% name a specific place while ~89% of every Reel is generic stock. Root cause was a rule in the old footage prompt: *"the FIRST TWO queries MUST include that city name"*. **Pexels never returns empty** — ask it for "deventer harbour" and it hands back the closest visual match from anywhere on earth. The rule *guaranteed* a wrong-place clip. No downstream check can repair this: stock libraries record no location, and no vision model can tell one small river harbour from another.
The fix inverts the rule — **prefer showing no place over the wrong place** — in five layers. The corollary was learned the hard way three days later: "no place" must still mean *the Netherlands*, or the account looks like it shows nowhere, which viewers read as fake just as readily (layer 5).
1. **Tiering, decided in code.** `generate_footage_queries` now returns `(queries, avoid, plan)`; the model extracts `place` + `place_type` (a task it does well), and `footage_geo.derive_place_mode` maps that to `stock_ok` (in `STOCK_SAFE_PLACES` — Amsterdam, Rotterdam, Schiphol… — or country scope) / `no_stock` / `none`. Asking Claude "is Deventer on Pexels?" would be exactly the unreliable judgement being designed out.
2. **Sanitizing on every query path.** For `no_stock`, place names and identifying framing (`skyline`, `aerial`, `cityscape`…) are stripped from AI queries, from the `extract_search_query` keyword fallback (which keeps raw Dutch words like `"deventer"` — the second, easily-missed injection path), and from `fetch_stock_image`'s Priority-3 photo query. Only `_NATIONAL_TERMS` (netherlands/dutch/holland) survive — note this is *narrower* than `STOCK_SAFE_PLACES`: for a Deventer story, "rotterdam port" is still the bug.
3. **Slug pre-filter, free.** Pexels returns a descriptive `url` slug the code used to discard. Three checks run on it before any vision call. `claims_a_place()` token-matches a mode-aware banned set (`slug_banned_places_for`): `no_stock` bans Dutch places (`NL_CITIES` + `_NL_PLACE_TOKENS` — ports/towns, **named rivers** and **provinces/regions**; a Deventer Reel shipped a **Harlingen** clip, and later seven **Nederrijn** clips for a story on the IJssel) + world landmarks/airports/**countries** (a Venray wildfire Reel took its cover from a clip slugged "farm fire in **south africa**"); `stock_ok` bans world places only while the story's own place stays allowed (a Schiphol Reel shipped **Kansai airport** footage). `shows_impossible_terrain()` rejects mountains/gorges/cliffs/desert/tropical in **every** mode — that names no place, so identifiability can't catch it, yet it single-handedly stops the Reel reading as Dutch. `claims_identifiable_framing()` rejects unnamed-settlement framing (`skyline`, `cityscape`, `aerial`+`city`) for `no_stock` only.
4. **One vision gate, four tests.** `validate_footage_thumbnails(..., place_mode=, place=)` runs a **single** criteria block for every mode — subject relevance, place claim, Dutch-possible terrain, avoid terms. It used to be two blocks and they drifted: only the `stock_ok` one mentioned relevance and only the `no_stock` one mentioned identifiability, so a **cosy-fireplace** clip passed a heatwave story either way (measured: 08-03, `stock_ok`, 14/15 passed). Test 1 therefore names the failure mode — decorative stand-ins that merely share a word with the story (fireplace/candle/match/campfire for a wildfire). In `stock_ok` mode the gate gets the concrete `place` so "wrong location" is checkable. Generically-Dutch **wide** shots (polder, canal, flat farmland, motorway) are an explicit PASS: the earlier "close, generic view that could have been shot anywhere" rule made every Reel look like nowhere, which viewers read as fake just like the wrong town did. The old fail-open floor (`<2 passed → use the top-2 clips the gate just FAILED`) stays **deleted**: candidates pool across queries and escalate to `_LAST_RESORT_QUERIES`, and returning `[]` is a valid outcome that degrades to a stock photo or gradient.
5. **"No place" must still mean the Netherlands.** Sanitizing a town story strips every geographic cue, so `footage_geo.ensure_national_anchor()` guarantees ≥`MIN_ANCHORED_QUERIES` (2) of the plan's queries carry `dutch`/`netherlands` — a **country** promise can never become a wrong-town claim. Enforced in `build_footage_plan`, not only in the prompt, because the live prompt lives in Secrets Manager and changes without a deploy. `_LAST_RESORT_QUERIES` is now `NATIONAL_ANCHOR_QUERIES` for the same reason — "abstract light bokeh" was the worst a news Reel could look.
Supporting changes: `COVER_SCENE_DURATION_PLACE = 7.0` plus a mid-Reel reprise of the article photo (the only footage that genuinely shows the place) — which required a new `lead_duration` param on `_stitch_clips_to_file`, since its even split made `COVER_SCENE_DURATION` a **no-op** before; a `build_source_label_overlay` "STOCK FOOTAGE · ILLUSTRATION" pill on stock segments, which directly refutes the "AI-generated" reading; `_search_pool` **interleaves** its queries round-robin instead of concatenating them (Pexels returns 20 hits per query and a Reel uses 9, so the first query used to supply *every* scene — one heat-record Reel ran nine Amsterdam canal clips in a row); and `footage_plan` + `footage_audit` (per-candidate accept/reject trail) persisted into `posts_*.json` — that audit trail did not exist, which is why this went unmeasured.

**Retention — 2 years, and it was previously unbounded (2026-08)**
There were **zero `ttl` blocks** in Terraform and **zero TTL attributes** written by any Python code, while `posts_*.json`, `articles_*.json` and `pipeline_results_*.json` at bucket root matched **no lifecycle rule**. Both `post-metrics` readers use `scan` + `FilterExpression`, whose cost tracks *total table size* rather than the 7–30 day window they ask for, so unbounded growth was a slowly rising bill on data nobody reads.
- **DynamoDB `post-metrics`**: TTL on `expires_at`, stamped by `metrics_collector` at `published_at + 730d`. Anchored to **publication, not collection** — `collect()` re-writes the trailing 30 days daily, so a `now`-anchored expiry would slide forward on every pass and never age out. TTL only deletes items that *carry* the attribute, so `local_only/backfill_metrics_ttl.py` stamps pre-existing rows once.
- **DynamoDB `prompt-versions`: deliberately NO TTL.** It is the rollback surface for prompt changes `analytics_engine` auto-applies above 0.80 confidence. If it ever needs bounding, cap by **count per `prompt_name`**, not by age — an old prompt that was working is exactly what you want to return to.
- **S3**: `articles_`/`pipeline_results_` expire at 730d; bucket-wide `noncurrent_version_expiration` at 730d (versioning is on and only `errors/` expired old versions before). **`posts_` is exempt from Glacier and expiry** — `get_published_urls()` reads every object's *body* for all-time URL dedup, so archiving would break URL dedup, the 3-day title window, the content mix, the violence cap and footage dedup at once, and expiring would let an old article be republished. It gets STANDARD_IA at 90d instead. Bounding it properly needs a compact all-time URL ledger first.

**Two silent-truncation bugs fixed with it.** Both read a paginated API as if it returned everything. (1) `get_published_urls` called `list_objects_v2` unpaginated — capped at 1000 keys, which the `posts_` prefix crosses around **day 500 (mid-2027)**; because keys sort as `posts_YYYYMMDD_HHMMSS` it would have returned the *oldest* 1000 and dropped every recent post, with no error. (2) `analytics_engine._load_previous_analysis` used `MaxKeys=10` then sorted by `LastModified` — **already firing**: past ten weeks it read the ten *oldest* files, so the week-over-week delta in the analytics email compared against an ancient baseline. Now paginates and sorts by key.

**Code quality metrics, measured per commit (2026-08)**
`scripts/code_quality/analyze.py` scores 7 metrics; `gate.py` compares against the previous commit and emails on regression; `backfill_history.py` replays history via `git archive`. Rendering is shared by CI and the weekly email through **`src/code_quality_report.py` — which lives in `src/` because `build_lambda.sh` does not copy `scripts/` into the ZIP**, and for the same reason the Lambda cannot read `pyproject.toml`, so thresholds ride *inside* `code_quality/history.json`. `tests/test_code_quality.py` asserts the fallback table matches pyproject (it has already caught one drift).

**Three numbers per metric, and conflating them is how a gate gets switched off:** *industry* (published best practice, source cited), *gate* (a hard ceiling set **above** today's baseline), *ratchet* ("worse than the previous commit" — the only thing that actually mails). Measured baseline: max CC **54**, mean CC 6.09, duplication 3.44%, coupling 15, DIT 2, LCOM4 2, MI 16.09, coverage 55.6%. **Four of the seven are already the wrong side of the industry figure**, so absolute gates at industry would alert on every commit forever.

**Depth-of-inheritance and LCOM4 are near-blind on this codebase and that is expected.** Across 99 commits and a 34× size increase they each moved 5 times and never exceeded 2 — they are Chidamber–Kemerer *class* metrics, and the largest module (`lambda_handler.py`) contains no classes at all. Class coupling is therefore measured at **module** level (efferent `Ce`), which is the direct structural analogue and does move. Duplication/coupling/DIT/LCOM4 are implemented in `scripts/code_quality/metrics.py` rather than delegated to pylint or a third-party tool **specifically so the definitions cannot shift under a dependency upgrade** — a definition that changes silently invalidates all 99 historical data points.

**`architecture/` — SDLC, runtime and data diagrams (Mermaid, renders on GitHub)**
`architecture/sdlc.md` is the delivery pipeline including a *"What nothing checks"* section (no rollback, no staging, no `terraform plan` on PRs, local-only secret scan, deploy role outside IaC, dead `check_readme_freshness()`); `runtime.md` is schedules/pipelines/model routing; `data.md` is storage and retention. `tests/test_terraform_schedule.py` asserts every Terraform cron appears in `runtime.md` and that both disabled rules are marked disabled — prose drifts, so the facts most likely to rot are pinned in CI.

## Analytics System (added 2026-06)

Collects per-post Instagram engagement metrics, normalizes them against follower count at time of publishing (to remove growth bias), runs weekly Claude analysis, auto-updates prompts, and surfaces everything in CloudWatch.

**New DynamoDB Tables**
- `news-ai-agent-post-metrics` — per-post engagement (normalized_engagement_rate = engagement/followers_at_publish×100)
- `news-ai-agent-prompt-versions` — versioned prompt history with change_reason + analytics_ref. Rollback = write an old version's `content` back to Secrets Manager.

**New Lambda handlers** (in `lambda_handler.py`)
- `handler_metrics_collector` — daily, fetches last 30 days of media + Insights from Instagram Graph API, writes to DynamoDB. Requires `instagram_manage_insights` permission on access token.
- `handler_analytics_engine` — weekly Sunday, queries DynamoDB, sends normalized data to Claude (`ANALYTICS_MODEL`, default `claude-opus-5`) for pattern analysis, auto-applies high-confidence prompt changes (>0.80), queues low-confidence ones for dashboard display, sends SNS diff email.

**Auto-decision thresholds**: prompt updates apply if confidence >0.75–0.85 AND min data ≥5–10 posts. Schedule/content-ratio changes are NEVER auto-applied — surfaced in CloudWatch Dashboard only.

**Dashboard**: CloudWatch Logs Insights queries pinned as dashboard widgets. Structured JSON logs use the stdlib pattern `logger.info(json.dumps({"event": ..., ...}))` — **not** `aws_lambda_powertools`, which is not a dependency of this project and appears nowhere in the code (this doc previously claimed otherwise). Event keys: `post_published`, `quality_gate_rejected`, `prompt_updated`, `selection_decision`, `viral_skip`, `post_metrics_updated`, and `claude_usage`. Match that shape when adding a new structured log or Logs Insights will not parse it.

**Source files**: `src/metrics_collector.py`, `src/analytics_engine.py`

## Known Gotchas

- **Failure emails come from Lambda async on-failure destinations** (`failure_alert` in terraform → SNS): every function routes any failed invocation (including timeouts) to the alert email.
- **Lambda import path**: `sys.path` inserts both `.` and `./src` at top of `lambda_handler.py` — necessary because local and Lambda ZIP have different structures.
- **Reels container polling**: Can take 8–10 minutes. Always happens in `reels_worker`, never in the main handler.
- **News Reel narration = hook + content**: `creator.create_news_video` narrates `hook + ". " + content`, then caps length via `tts.cap_narration(text, MAX_NARRATION_WORDS=120)`. The cap truncates **on sentence boundaries only** — never mid-sentence. The earlier raw 100-word cut clipped the final sentence's tail (an 11-word hook + 96-word content = 107 words lost "...in 1928 during the Amsterdam Summer Games."). Content is prompt-capped to 75–95 words, so 120 comfortably fits hook+content; if it ever overflows, whole trailing sentences drop, not half of one.
- **EventBridge cron times are UTC**: All schedules in Terraform are UTC. Amsterdam = UTC+1 (winter) / UTC+2 (summer, CEST). The current crons assume CEST (+2) — may be off by 1 hour in winter.
- **Pexels lazy-loading**: `footage.py` uses pagination with lazy fetching; don't call `len()` on the generator directly.
- **Instagram Insights requires separate permission**: `instagram_manage_insights` must be added to the Meta App for `handler_metrics_collector` to work.
- **S3 bucket name**: hardcoded fallback in `lambda_handler.py` as `news-ai-agent-results-645949963620`. Override via `RESULTS_BUCKET` env var.
- **Lambda ZIP size limit**: unzipped package must stay under 250 MB. Current size ~231 MB. `build_lambda.sh` aborts if >240 MB (safety gate). Key exclusions: `googleapiclient/discovery_cache/documents/` (all except `youtube.v3.json`) and `zstandard/`. If a new heavy dependency is added and the limit is hit, migrate to Lambda Container Image (ECR, no size limit).
- **YouTube OAuth token**: invalidated if user revokes access or GCP OAuth app is in Testing mode (tokens expire in 7 days — must be Production). Fix: re-run OAuth Desktop flow locally, update `YOUTUBE_REFRESH_TOKEN` in Secrets Manager.
- **YouTube vs events**: events Reels (slide-based PIL video) is published to Instagram only. YouTube receives news Reels only. See architectural decision above for rationale.
- **LinkedIn vs events**: like YouTube, LinkedIn receives **news Reels only**. The exclusion is enforced inside `build_crossposter()` — the event pipeline calls `build_crossposter(content_source="event")`, which skips LinkedIn registration. Call sites stay channel-agnostic (they pass a *content source*, never a channel name).
- **LinkedIn needs raw bytes, not a URL**: unlike Meta's `file_url` fetch, LinkedIn's Videos API uploads bytes. `LinkedInPublisher.publish_reel` downloads the presigned S3 URL into memory first — fine because Reels are short (<~50 MB); if a much larger video is ever published this would need streaming/chunking. Required headers on every call: `LinkedIn-Version` (YYYYMM) + `X-Restli-Protocol-Version: 2.0.0`; the created post id comes from the `x-restli-id` response header, not the body.
- **Instagram Stories API limits**: `media_type=STORIES` containers accept **no caption** and **no interactive stickers** (polls/questions/links are app-only). The daily fact's text is baked into the video. Story reach is mostly existing followers, not discovery — Stories are a retention/completion surface, not a growth channel.
- **`ENABLE_INSTAGRAM_STORIES` is checked twice**: first in `_run_daily_fact_pipeline` (so flag-off costs nothing), again in `reels_worker` (defense-in-depth before any Story publish). Both read the same Secrets Manager value.
- **The weekly events post is disabled at two layers** (deprecated for low engagement): (1) the Thursday EventBridge rule `events_thursday_schedule` is `state = "DISABLED"` in Terraform, so the cron never fires; (2) the `ENABLE_EVENT_POSTS` feature flag (Secrets Manager, default off) gates the pipeline itself — checked in the `event_post` dispatch branch (short-circuits before building the AI agent) and again at the top of `_run_event_pipeline` (defense-in-depth for manual/async invokes). Flag-off costs nothing (no scrape/scoring/render). **Re-enable = both: flip the rule to `state = "ENABLED"` in Terraform AND set `ENABLE_EVENT_POSTS=true` in Secrets Manager.** The event-only `[Analytics Optimization]` blocks in `AI_PROMPT_EVENT_SELECTION` are intentionally kept (they only affect event curation, never news, and apply again on re-enable). While events are off, `analytics_engine` skips `event_curation` recommendations so it never appends to the now-dormant event prompt.
- **Facebook Page Stories need `pages_manage_posts`**: the Meta user token (`INSTAGRAM_ACCESS_TOKEN`) must hold the `pages_manage_posts` scope, or `video_stories` returns `(#3) Application does not have the granular permission`. Re-issue the token via `scripts/get_new_instagram_token.py` selecting that scope. The connected Page (name "Dutch Daily", id in `FACEBOOK_PAGE_ID`) has its Page token derived from the user token at runtime — no separate token is stored. The 30-day refresh Lambda preserves the scope.
- **Never add a new `{placeholder}` to a Secrets Manager prompt**: the prompt is edited independently of a deploy, so a new placeholder makes prompt and code a matched pair — publish the prompt first and the *running* Lambda raises `KeyError` inside `.format()`, which `process_batch` swallows into the `process_article(articles[0])` fallback. That fallback returns a post successfully, so nothing alerts: the slot silently publishes the first scraped article with no tiers, no dedup and no CTA. The slot brief and content mix are therefore **prepended** to the rendered template, not substituted into it, and `tests/test_editorial_selection.py::test_live_prompt_needs_no_new_placeholders` renders the live prompt with the old kwarg set to keep it that way. Same reasoning applies in reverse — deploying code that *requires* a prompt field before the prompt ships.
- **`scripts/update_secrets.py` silently DROPS prompt keys**: it builds a payload with only `AI_PROMPT_BATCH_SELECTION`, `AI_PROMPT_SINGLE_ARTICLE` and `AI_PROMPT_QUALITY_CHECK`, then calls `update_secret` — which replaces the whole secret. Running it **wipes `AI_PROMPT_EVENT_SELECTION`, `AI_PROMPT_CAROUSEL_CAPTION` and `AI_PROMPT_FOOTAGE_QUERIES`**. To add or edit a prompt in Secrets Manager, merge by hand: `get-secret-value` → edit JSON → `put-secret-value`.
- **Never name a small place in a Pexels query**: Pexels always returns *something*, so a query naming a town you have no footage of returns a **different** town — which viewers read as an AI-generated fake. `footage_geo` strips place names for `place_mode == "no_stock"` stories at three separate call sites; if you add a fourth query path, sanitize it there too. `STOCK_SAFE_PLACES` (places we may name at all) is deliberately wider than `_NATIONAL_TERMS` (places any story may name).
- **…but never let sanitizing leave the Reel with no country either**: stripping the town also strips "the Netherlands", and a Reel of place-free close-ups reads as stock slop. `ensure_national_anchor` therefore *appends* `dutch`/`netherlands` queries (never substitutes — the story's own queries keep the cover). If you add a filter that can empty the query list, re-check the anchor count afterwards.
- **The vision gate is ONE criteria block on purpose**: it used to branch on `place_mode`, and the two branches drifted until only one asked about relevance and only the other about identifiability — which is how a heatwave story shipped cosy-fireplace footage at a 14/15 pass rate. Adding a mode-specific rule means adding a *line* inside the single block (like `place_rule`), never a second block.
- **The keyword fallback query is a replacement, not an addition**: `extract_search_query` keeps untranslated Dutch, and a live run really searched Pexels for `uitzonderlijke situatie droogte brand`, then scored the results as though they were about drought. `fetch_stock_clips` uses it **only when the AI produced no queries at all**. Don't append it "just in case".
- **`_search_pool` interleaves, and that is load-bearing**: Pexels returns 20 hits per query while a Reel uses 9, so concatenating the pool let the first query supply every scene (nine Amsterdam canal clips in one Reel). Round-robin keeps the first query's top hit as the cover while the rest of the Reel spans all three pooled queries — this is where within-run visual variety comes from.
- **Footage repetition across days is NOT covered by the dedup ledger**: `posts_*.json` records `pexels_media_ids` only, so three consecutive fire stories can ship three visually identical fires with three different ids (measured 08-03 → 08-04: `burning-firewood-in-the-fireplace` → `bonfire-slow-motion` → `close-up-of-burning-firewood`). The subject-relevance and terrain tests remove that *class* of clip at source, but nothing tracks visual themes over time. If it resurfaces, the fix is to persist slugs alongside ids and demote recent slug tokens in `_fresh_first` — not to widen `FOOTAGE_REUSE_WINDOW_DAYS`, which the id data shows is already doing its job.
- **TTS pronunciation: subtitles come from the SPOKEN text**: subtitle segments derive from the character alignment of whatever string was sent to TTS, so pronunciation fixes must respell for the engine and then `restore_display_words()` on the returned segments — writing phonetic spellings straight into narration text puts them on screen. Respellings are unique single tokens precisely so restoration is a safe reverse lookup. Extend without redeploy via `TTS_PRONUNCIATIONS` (JSON in Secrets Manager). The debug `subs.srt` intentionally keeps the spoken (respelled) text.
- **`COVER_SCENE_DURATION` only works with `lead_duration`**: `_stitch_clips_to_file` splits time evenly unless `lead_duration` is passed, so raising the cover constant alone changes nothing — the 4.0 s cover was really 3.5 s for a long time.
- **A handler that returns a 500 dict is a SUCCESS to Lambda**: no `Errors` datapoint, no alarm, no on-failure destination, no retry. The main handler therefore re-raises after alerting (`maximum_retry_attempts = 0` makes that safe); the async workers deliberately do not (`retries = 2` would republish). Before adding a new `except`, decide which of the two shapes it needs — this is the single easiest way to make a failure invisible again.
- **The viral check reads the Graph API live, never DynamoDB**: `metrics_collector` runs once daily at 00:00 UTC, so the metrics table holds **nothing** about a post published at 09:00 or 19:00 the same day — exactly the window virality happens in. `viral_guard` therefore calls `GET /{account_id}/media?limit=1` + `_post_insights()` live, and uses DynamoDB **only** for the median baseline (mature posts from previous days). Don't "optimize" the live calls away.
- **Viral-skip thresholds must be read at CALL time, not import time**: `VIRAL_SKIP_MULTIPLIER` (5.0), `VIRAL_MIN_ENGAGEMENT` (1000), `VIRAL_WINDOW_HOURS` (24), `MIN_BASELINE_POSTS` (10) go through `viral_guard._tunable()` inside the invoke. A module-level `os.environ.get(...)` constant (the `FOOTAGE_REUSE_WINDOW_DAYS` pattern) would **not** work here: it evaluates at container init, before `get_secrets()` copies the values out of Secrets Manager, so a retune would silently never apply. `get_secrets()` must also list each key — a threshold that isn't copied there is unreachable from the secret. Deleting `s3://<bucket>/viral/_skip_state.json` re-arms the guard for a post it already skipped for (only useful in testing).
- **`events_reel` is an analytics label, not a format the pipeline can produce**: format is decided solely by the EventBridge payload. `metrics_collector._post_type` used to guess `events_reel` from caption keywords ("events", "this week", "festival"), which mislabelled ordinary news Reels and made the weekly review recommend "default to the events_reel format" — a format that does not exist. It now returns `"reel"` for every Reel while `ENABLE_EVENT_POSTS` is off. **The weekly reviewer reasons from `posts_*.json` + DynamoDB, not from the code** — a mislabel there becomes a confident wrong recommendation.
- **EventBridge crons are UTC, and the weekly review will misread them**: `cron(0 17 * * ? *)` *is* 19:00 CEST. A review suggestion to "move the evening post to 19:00 CEST instead of 17:00 UTC" is asking for what already ships. Check the timezone before acting on any schedule recommendation.
- **Content-mix tunables must be read at CALL time**: `CONTENT_MIX_WINDOW_DAYS` (7), `VIOLENCE_SHARE_CAP` (0.40), `TOPIC_SHARE_CAP` (0.30) and `SERIES_MAX_DAYS` (4) go through `lambda_handler._mix_tunable()` inside the invoke, for the same reason as the viral-skip thresholds — a module-level `os.environ.get` evaluates at container init, before `get_secrets()` copies the values out of Secrets Manager, so a retune would silently never apply. All four keys are also listed in `get_secrets()`. `_MIN_SATURATION_POSTS` (3) is deliberately **not** a secret: it is a statistical floor, not a policy dial.
- **Never add a selection rule whose metric the weekly reviewer cannot see**: the reviewer's payload is what closes the loop, and `shares` was missing from it for the entire life of the save-optimised ranking. The rule looked correct, every metric the review could see stayed flat, and the account lost its whole breakout tail before anyone noticed. If a new rule targets a signal, add that signal to `_attach_engagement` in the same change. `FOOTAGE_REUSE_WINDOW_DAYS` still uses the import-time pattern and is *not* hot-tunable.
- **Fact rotation is hot-editable, no redeploy**: to add/change facts, edit `s3://<bucket>/facts/pool.json` directly. New entries (unseen `id`s) jump to the front of the LRU rotation. `DEFAULT_FACTS` only seeds the pool on first run when `pool.json` is absent.
- **`ruff`'s rule set is narrow *because* it blocks the deploy**: `E4,E7,E9,F,B` only. `E501`/`UP`/`I`/`SIM` report ~700 findings between them; enabling a family without the cleanup commit that makes it pass turns a blocking gate permanently red, and a permanently-red gate gets switched off. Widen one family at a time, each with its cleanup. `E402` is per-file-ignored for the six modules that must mutate `sys.path` before importing.
- **`bandit` blocks on `-lll` (HIGH) not `-ll` (MEDIUM)**: there are 22 MEDIUM findings, 19 of them `requests` calls with no timeout — a genuine reliability bug in a Lambda on a 15-minute hard limit, and worth its own change, but blocking on it today would just mean the gate never ships. `B108` (hardcoded `/tmp`) is skipped globally: `/tmp` is the only writable path in a Lambda, so every hit is by construction.
- **`get_secrets()` must list every hot-tunable key** — this now includes the six model knobs (`CONTENT_MODEL`, `REVIEW_MODEL`, `FOOTAGE_QUERY_MODEL`, `VISION_MODEL`, `ANALYTICS_MODEL`, `SELECTION_REVIEW_MODEL`). They were readable from the environment but never copied out of the secret, so they were deploy-only in practice while being documented as hot-tunable. Same trap as the viral and content-mix thresholds.
- **`VALIDATION_BATCH` must stay ≤ `ai_agent.VISION_BATCH_LIMIT`**: `footage.py` zips its candidate batch against the verdicts the gate returns, and the gate applies its own cap. A caller batch larger than the gate's limit would silently drop the surplus clips **unjudged and unaudited** — the exact invisible-footage-failure class the audit trail exists to catch. The zip is `strict=True` and `tests/test_footage_geo.py` asserts the relationship, so a mismatch fails in CI rather than mid-render.
- **`event_scraper` RSS parsing relied on `Element.__bool__`**: `item.find(tag) or item.find(tag, ns)` — an `Element` with no children is **falsy**, which is the normal case for `<title>text</title>`, so the namespaced lookup ran for every plain field (and emitted a DeprecationWarning 36× per test run). Now an explicit `is None` check. Note `find("atom:link")` without a namespace map raises `SyntaxError`, swallowed by the outer `try` — atom feeds are likely still broken, unfixed and out of scope while events are disabled.
- **`analytics/` and `learnings/` are gitignored**: `analytics/` holds audience-report output and the code-quality history; `learnings/` holds plans and blog drafts. One-time scripts go in `local_only/`. The analytics *scripts* are written in `local_only/analytics_scripts/`, run, then **deleted** — but `analytics/data/` (the raw API pulls) is kept, so a future throwaway script can re-slice saved JSON instead of re-fetching. Comment fetching is the slow, rate-limit-exposed part.
- **Instagram exposes no follower list and no liker list**: the only individuals the API will name are **commenters** (`/{media-id}/comments`). Whole-audience country data comes from one place only — `GET /{ig-user-id}/insights?metric=follower_demographics&breakdown=country` (needs `instagram_manage_insights`, ≥100 followers). Any per-person geography is inference over the engaged subset, and the two must never be merged into one number.
- **Pillow cannot be upgraded past 11.x while moviepy is a dependency**: `moviepy` 2.2.1 (latest) pins `pillow<12.0`, and `pip-audit` reports **25 CVEs in pillow 11.x whose fixes all land in 12.1.1–12.3.0**. Setting `Pillow>=12.3.0` makes the build unresolvable — the Lambda ZIP fails to install. `>=11.3.0,<12.0` is the most-patched release moviepy permits. The real fix is **dropping moviepy**: the news Reel path already renders via ffmpeg (`video/ffcompose.py`) and only `create_fact_video` (daily Story) still uses it. This is the concrete reason `pip-audit` runs `continue-on-error` in CI — a transitive pin you cannot unilaterally fix must not block an unrelated hotfix.
- **`src/fonts/NotoEmoji-Regular.ttf` was a 300 KB HTML page, not a font** (a GitHub *page* saved instead of the raw file). It was copied into every Lambda ZIP and never noticed, because the only thing pointing at it — `video/config.FONT_EMOJI_PATH` — was itself unused. Both are removed. If emoji rendering in PIL is ever wanted, download the real file and check `file src/fonts/*.ttf` says "TrueType Font data" before committing it.

**The 2026-08-02 cost jump, and what actually caused it**
Daily Claude spend went from ~$0.16/day to a measured **$0.61/day (3.7×)** on 2026-08-02. Nine commits landed that day and **four compounding changes** did it — not one:
1. **Vision model: `haiku-4-5` ($1/$5) → `opus-5` ($5/$25)** — 5× on the dominant term.
2. **Vision calls: 1 → 0-2** — `6988f15` added the pooled search + escalation ladder. Combined with (1) this alone made vision **10×**, and vision is **58% of a run**.
3. **`max_tokens` raised 3-8× everywhere** by `33b68f0` (vision 400→3000, batch 3000→8000) to make room for Opus 5's default-on thinking — and thinking bills as **output** tokens at $25/MTok.
4. **Batch-selection prompt: 24 → 158 lines** (`bb6eaa5`) — more input on every run, forever.

**The vision gate is INPUT-dominated** (~29.6k in vs ~1.1k out across two calls), so the lever is the input price per token and the number/size of images — *not* the model tier's reasoning quality. Downgrading Opus 5 → Opus 4.8/4.6 saves **nothing**: all three are $5/$25. Only Sonnet ($3/$15) and Haiku ($1/$5) are actually cheaper.

**Do not call a move to Haiku "a revert".** The gate ran on Haiku only in its *older, two-layer* form; the current four-test geo-aware gate (`6988f15`) and the Opus 5 migration (`33b68f0`) landed the **same day**, so this gate has never run on Haiku. Sonnet 5 is the floor until `footage_audit` data says otherwise.

**Effort is now per-role and read at CALL time** (`ai_agent._effort_for`, env `EFFORT_<ROLE>`, copied by `get_secrets()`), because it is the cheapest lever available: it changes how much the model thinks without changing which model runs. Right-size `max_tokens` alongside it — the vision call was capped at 3000 while measuring 502-606 output tokens, so the ceiling only ever bought thinking.
- **Vision-gate A/B (`VISION_SHADOW_MODEL`, default off)**: set it and the gate runs a challenger on the *same* thumbnails, logs a `vision_shadow` event and writes one sample to `s3://<bucket>/vision_ab/`; `analytics_engine._vision_ab_section` summarises the last 7 days into the Sunday email, and the section is omitted entirely when no experiment is running. **The verdict is driven by the LOOSER count, never by the agreement rate** — a challenger that PASSES a clip the primary FAILED would ship exactly the wrong-place / wrong-subject footage the gate exists to stop, so 99.5% agreement with one looser call is still `DO NOT SWITCH`, while stricter disagreements only waste money (more escalation). The shadow call is flag-gated, wrapped, never touches the primary verdict, and its own cost is logged separately under `role: "vision_shadow"`. Samples expire after 90 days so a bounded experiment cannot leave an unbounded prefix.
